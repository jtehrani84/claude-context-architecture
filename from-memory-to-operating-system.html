How Corrections Turned into Autonomy

Nobody planned a 2.1 GB local intelligence system, least of all me. Each correction, wiki page, and skill came out of a specific session's need, and the five-tier framework from Part 1 gave those decisions somewhere to land.

Claude would make a mistake and I'd correct it, and that correction got saved as a memory file. If the same mistake kept coming back I had Claude write a rule for it, and the rules it still ignored got turned into hooks. Some of those hooks needed real data before they could decide anything, which is how MCP servers came in, and once the servers started overflowing the context window I brought in context-mode to absorb them. Each layer showed up because the one before it wasn't enough by itself.

I'm not a developer, and sixty days of this didn't make me one. I haven't written a line of Python, authored a YAML skill file, or debugged a hook script, and I've never hand-built a skill either. Claude built every piece of the infrastructure (the hooks, the graph indexer, the skills) from my requirements, so what it took from me was knowing what I wanted and being specific about the constraints.

The pace picked up as the layers stacked. The first twenty days were memory and the wiki, basically the filing system, then days 20 to 40 added hooks and MCP servers for enforcement, and days 40 to 60 brought skills, the graph, and context-mode. Each layer made the next one faster to build, so by day 60 Claude could stand up a new skill in about 5 minutes because it already had the patterns from the previous 179.

From Passive to Active

Part 1 described a passive system that stored things and loaded them when they were relevant. What grew out of it acts on its own. It intercepts and enforces without a human in the loop, and it checks its own output before anything ships.

"Memory persists corrections" → Memory is entity-linked, graph-indexed, auto-curated

The Pattern

Every passive piece ended up pulling in an active counterpart. Storage got enforcement sitting next to it, reference material got validation, and memory got curation, which looks a lot like the system growing an immune response to the specific ways it kept failing.

Entity Pages for the People

Memory holds corrections and the wiki holds knowledge, and for a while nothing held people. Entity pages fill that gap with a structured page per person that compounds across every interaction.

There are two templates, internal and external. The structured top gives you instant prep (role, org position, working style, territory), and an append-only timeline below it grows with every meeting, decision, and collaboration. The pages are seeded programmatically from Slack profiles, then enriched by overnight intelligence crons.

WithoutWith entity pages
"Who's the AE on that account?" → Full org tree with SE/AE assignments in one Read
"What did we discuss last time?" → Timeline shows every interaction chronologically
Meeting prep = 20 min searching → One page, auto-routed by SessionStart hook

By day 60 that was 150+ people mapped across the sales and solutions org trees, each leader sitting there with their reports, Slack IDs, and coverage areas. The CRM has the accounts, and I wanted somewhere that held the humans working them.

Where the Layers Interact

Each layer is useful by itself, but most of the payoff came from the places where one hands off to the next, and three loops show it best.

The first one starts with a mistake. Deploy with --set-env-vars instead of --update-env-vars and every env var gets wiped. You correct Claude, the correction lands in memory, that memory gets cited in an infrastructure rule, and from then on a hook blocks any deploy that uses --set-env-vars, so that whole class of error is gone, even in a fresh session with nothing loaded yet.

The second is research turning into routing. When I researched Agentforce Agent Script, Claude wrote it up as a wiki page and the graph pulled the entities out of it, so the next time I mention "agent routing" the SessionStart hook surfaces that page along with the related memories and the architecture doc before I've asked for any of it.

The third is a skill doing the driving. When I run /account-prep the skill already knows the workflow, so it calls the MCP servers for CRM, news, and web, compresses each response through context-mode, and assembles the prep doc under the anti-slop rules and corporate grounding. That's one command driving five systems, and I don't manage any of the context by hand.

If any one of those layers is missing, the loop doesn't close. Memory on its own never blocked that deploy, and the hook only knew the flag was dangerous because memory told it, the same way a skill is stuck with local files until an MCP server gives it outside data.

Agents Forget to Remember, at Every Layer

In Part 1 I cited DDR-001 from the Agentforce Agent Harness and its line "agents forget to remember," and the fix at the time was intrinsic constraint awareness. Two months on, the same failure shows up at every layer of the stack.

Layer"Forgetting" Failure ModeFix
MemoryDoesn't check before claimingGraph recalls relevant memories proactively
RulesReads but ignores under pressurePreToolUse hook intercepts before execution
SkillsReinvents instead of loadingSkill routing matches task automatically
WikiPattern-matches from training dataADR hook injects decisions when files in scope
MCPHallucinates instead of queryingGrounding rules require real data queries

My 128 memory files never stopped my infrastructure mistakes and three PreToolUse hooks did, which is how I ended up believing every knowledge source needs a matching enforcement mechanism. Knowledge that only sits in context gets quietly skipped once a session gets busy, and the same knowledge sitting behind a hook keeps holding session after session.

Outside Validation

When Part 1 went out this all felt like a personal hack, and four weeks after I published it that stopped being true.

Karpathy's "LLM Wiki" hit 5,000+ GitHub stars. The pattern I'd built on, ingest-synthesize-evolve, went viral and spawned a wave of persistent memory tools, and by then I'd been running it in production for months. His own comment on it is the one I keep coming back to.

“I think there is room here for an incredible new product instead of a hacky collection of scripts.”

Andrej Karpathy, on the LLM Wiki pattern

Sixty days after Part 1, my own hacky collection of scripts had become a platform, and I hadn't designed it to. Salesforce's VP-level Futures team published "Not All Agentic Harnesses Are Created Equal" on the exact framework I'd been living in, the scaffolding that gives a model its tools, data, and constraints, which I took as direct validation at the highest level. Anthropic shipped Managed Agents with a memory consolidation feature they called "dreaming," agents consolidating what they learned between sessions, the same pattern as my memory and /curate system, productized by Anthropic themselves.

By May 2026 MCP token overhead was a known problem too. At 58 tools you burn about 55K tokens per turn, and I was already running more than 200 with deferred loading, so for me that one was already solved.

What Context Actually Buys You

Part 1 solved one specific problem, Claude forgetting between sessions. The system that grew out of that fix ended up going after a much bigger one... making a non-developer as productive as a senior engineering team.

My best evidence for that is my own build history. Over 28 days, 199 commits built an AI platform with 6 subagents, 25 data connectors, and production infrastructure, and that was on the early five-tier system. On the day-60 stack the same scope takes less than a week. The models getting smarter doesn't explain that. What kept closing the gap between domain expertise with clear requirements and production software was the local infrastructure around the model compounding, and none of it asked me to be a developer.

The two case studies below come at that from different directions, one about intelligence and one about autonomy.

The Starter Kit

It took me 60 days of trial and error to get here, and the whole architecture is packaged as a deployable kit so you can clone the repo, run setup, and start from Day 30 instead of Day 0.

The architecture, templates, and feedback loops all transfer. The 220+ specific memories don't, because those are my corrections and my project state and yours will look different, so the kit hands you the scaffolding and compound learning fills it in over time.

The Kit (5 Layers, 45 Minutes to Deploy)

Layer 1, the identity skeleton, is a template CLAUDE.md with the routing-table structure, role definition, project registry, and essential standards baked in (anti-slop, anti-hallucination), plus a pre-wired wiki index. Filling in your own role, projects, and constraints takes about 10 minutes.

For rules and guardrails (layer 2), the three starter rules files are communication.md for voice standards and banned patterns, security-governance.md for CRUD/FLS, sharing, and secrets, and architecture.md for the decision framework and preferred patterns. It also ships two hook scripts, session-init for context routing on start and one PreToolUse guardrail that blocks your most expensive recurring mistake.

Then there's the SE skill pack, five production-ready skills that each replace about 30 minutes of manual instruction per use: /account-prep for pre-meeting intelligence, /deal-strategy for competitive positioning and a talk track, /email-draft for anti-slop customer email, /post-meeting for capture, CRM, and follow-up, and /demo-prep for a script built from a brief.

The fourth layer is intelligence automation, a Slack channel roster of 25 pre-mapped internal channels (product, competitive, enablement, win/loss, leadership) and overnight gather scripts that scan Exa, HN, GitHub, X, and Slack and synthesize a morning brief. There's one MCP server (GitHub) in there to prove the action layer works. Swap in your own OU channels and go.

Last come the entity pages, a wiki/people/ directory with the two templates, internal and external. You seed your org tree from Slack profiles, with Claude pulling name, title, email, and timezone programmatically, and each page puts org position at the top with an append-only timeline below it. After one session every leader and their reports are mapped, and after a month you've got a relationship graph no CRM captures.
